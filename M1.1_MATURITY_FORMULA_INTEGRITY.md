# M1.1 — Maturity Formula Integrity Review

Design clarification exercise, per the M1.1 brief. No application code,
migrations, schema changes, UI, or implementation-requiring tests were
created. This document amends and corrects two specific parts of
`M1_MATURITY_DESIGN.md` (M1) — it does not re-litigate the rest of that
document, which stands.

---

## 1. Finding — MaturityAssessment lifecycle

**The intended lifecycle is: one finalized Assessment (initial or a later
reassessment) → exactly one computation event → immediate finalization.
`draft` is a brief, single-transaction technical intermediate state, not
a scratch pad for iterative review-and-revise. "Delete draft and
recompute," which M1 §21 listed as a REQUIRED FOR MVP function
(`discardDraftMaturityAssessment`), is NOT supported by the existing
schema and security model, and that recommendation is withdrawn — see
§9 below.**

Point-by-point:

1. **Why does `MaturityAssessment` have draft/finalized state at all?**
   Not to allow review-then-edit. It exists because writing "one
   `MaturityAssessment` header row plus N `MaturityScore` child rows" is
   inherently a multi-statement operation, and `MaturityScore` rows may
   only be **inserted** while their parent is `draft`
   (`enforce_maturity_score_draft_mutable`, migration `0015` §7). `draft`
   is the state that exists for exactly as long as it takes to insert all
   the score rows for one computation; `finalized` is the permanent,
   locked, historical state. DECISIONS.md R-76 confirms this reuses
   `Assessment`'s own "simple finalized state" vocabulary verbatim,
   not an invented `computed`/`reviewed`/`published` workflow.

2. **When is a `MaturityAssessment` created relative to Assessment
   finalization?** Strictly after — `require_finalized_assessment_for_
   maturity` (migration `0015` §6, BEFORE INSERT) rejects creation unless
   the referenced `assessments.status = 'finalized'`
   (`tests/maturity/immutability.test.ts:141-148`, "cannot create a
   MaturityAssessment from an Assessment that is not finalized"). This
   also matches DATA_MODEL.md §9's own trigger language: "`MaturityScore`
   rows are produced only by the Maturity engine's recalculation
   routine, triggered by an accepted `ValidationRecord` leading to a
   control reassessment, **or by a new `Assessment` finalization**" — in
   both cases the proximate trigger is an `Assessment` finalizing (a
   reassessment is itself a new/updated `Assessment` that gets
   finalized), never a standalone "recompute" action on existing,
   unchanged data.

3. **When are `MaturityScore` rows created?** During the `draft` window
   of one `MaturityAssessment`, one INSERT per in-scope domain plus one
   INSERT for the overall (`maturity_domain_id IS NULL`) row — every real
   test (`crud.test.ts`, `historical-scenario.test.ts`,
   `immutability.test.ts`) creates the `MaturityAssessment`, inserts all
   its `MaturityScore` rows, and calls `finalizeMaturityAssessment` in
   the same `beforeAll`/`it` block, back-to-back, with no intervening
   review step ever exercised.

4. **Can a draft `MaturityAssessment` be recalculated?** No — not by
   editing existing rows. Header fields other than the frozen identity
   columns (`computed_from_risk_ids`, `computed_from_validation_record_
   ids`, etc.) remain UPDATE-able while draft
   (`immutability.test.ts:159-173`, "ordinary fields remain editable
   while draft"), but the `MaturityScore` **child rows that carry the
   actual numbers are not** — see next point. "Recalculating" a draft in
   the sense of changing its computed scores has no supported path.

5. **Can existing `MaturityScore` rows be deleted/replaced while the
   `MaturityAssessment` is still draft?** **No — proven directly, not
   inferred.** `tests/maturity/immutability.test.ts:233-246` ("no
   UPDATE/DELETE grant exists on MaturityScore — a computed score can
   never be edited or removed") creates a fresh `MaturityScore` against a
   `MaturityAssessment` that is **still draft (never finalized in that
   test)**, then attempts `UPDATE ... SET score = 5` and `DELETE FROM
   maturity_scores` — both are rejected with `permission denied`. The
   migration grants confirm why: `GRANT SELECT, INSERT ON
   "maturity_scores" TO authenticated` (migration `0015` §11) — no
   UPDATE, no DELETE, unconditionally, regardless of the parent's
   status. Additionally, `noDuplicateDomainScore` (unique on
   `maturity_assessment_id, maturity_domain_id`) blocks re-inserting a
   corrected score for the same domain under the same `MaturityAssessment`
   even once — a second INSERT for that domain fails as a duplicate.

6. **What exactly becomes immutable when `MaturityAssessment` is
   finalized?** Two independent layers, already fully immutable/closed
   before finalization for `MaturityScore`, newly closed at finalization
   for the header itself:
   - `maturity_assessments`: every field, "not even a no-op"
     (`enforce_maturity_assessment_finalization`, migration `0015` §5;
     proven in `immutability.test.ts:184-200`, including a rejected
     attempted `status = 'draft'` un-finalize).
   - `maturity_scores` belonging to it: were already 100% immutable from
     the instant of creation (point 5); finalization additionally closes
     the **set** — no further row may be **inserted** at all
     (`enforce_maturity_score_draft_mutable`, same migration §7;
     `immutability.test.ts:248-257`).
   So finalization's real effect is narrower than it first appears: it
   doesn't "lock scores that were previously editable" (they never were)
   — it locks the **header** and closes the **set membership** of scores
   permanently.

7. **Is "delete draft and recompute" actually supported/intended?**
   **No.** There is no DELETE grant on `maturity_assessments` (migration
   `0015` §11 grants only `SELECT, INSERT, UPDATE`) and no DELETE grant
   on `maturity_scores` (`SELECT, INSERT` only). A wrong or abandoned
   draft `MaturityAssessment` cannot be deleted through any ordinary
   path, and its `MaturityScore` rows cannot be corrected or removed
   either. This directly contradicts M1 §21's "REQUIRED FOR MVP" listing
   of `discardDraftMaturityAssessment` — that function cannot be built
   as specified without a new migration granting DELETE (a real schema
   change, correctly out of scope for a design-only exercise, and not
   clearly warranted — see §3 and §9 below for the recommended
   alternative).

8. **Is there any existing mechanism for creating a new
   `MaturityAssessment` for the same Assessment?** No blocking
   constraint exists — `maturity_assessments` has no `UNIQUE
   (assessment_id)` (only `idScopeUnique` on
   `(id, tenant_id, organisation_id, engagement_id)`,
   `db/schema/maturity-assessments.ts:108-113`), so nothing at the
   database layer stops a second `MaturityAssessment` row from being
   created against the same `assessment_id`. No test exercises this
   (`historical-scenario.test.ts`'s MA1/MA2 are against two *different*
   Assessments, FY2026/FY2027, never the same one twice), and no
   DECISIONS.md entry addresses it. **This is a genuine, undecided gap**
   — flagged as an open decision in §10, not resolved by inventing
   behavior.

9. **What should happen if the underlying `AssessmentResponse` data
   changes before `MaturityAssessment` finalization?** **This cannot
   happen, by construction — the question's premise doesn't arise.**
   `require_finalized_assessment_for_maturity` requires the source
   `Assessment` to already be `finalized` before a `MaturityAssessment`
   can even be created (point 2); and `assessments`' own finalization
   trigger family already freezes `assessment_responses` and
   `assessment_controls` (including the D3 `applicability_decision`/
   `applicability_rationale` snapshot columns) the moment the *Assessment*
   itself finalizes — "cannot % an AssessmentResponse on a finalized
   assessment" / "cannot % an AssessmentControl on a finalized
   assessment" (migration `0009`, lines ~185-223). So by the earliest
   possible moment a `MaturityAssessment` can exist, its entire input
   surface (`AssessmentResponse.effectiveness_rating`,
   `AssessmentControl.applicability_decision`) is already permanently
   frozen. There is no window, draft or otherwise, where the inputs
   could shift underneath a `MaturityAssessment`.

### Recommended lifecycle (revised from M1 §21/§19)

```
Assessment finalized (initial, or a later reassessment)
  → (inputs are now permanently frozen — see point 9)
  → application computes the full result in memory
      (all domain scores + the overall score)
  → ONE transaction:
      INSERT MaturityAssessment (status='draft')
      INSERT one MaturityScore per in-scope domain
      INSERT one overall MaturityScore
      UPDATE MaturityAssessment SET status='finalized'
  → immutable historical result

If the computation was wrong (bad input selection, application bug,
wrong methodology pinned): the flawed MaturityAssessment is NOT deleted
and NOT corrected in place — both are structurally unsupported (points 5,
7). It is left as a permanently orphaned, un-finalized draft (harmless:
nothing reads an unfinalized MaturityAssessment as authoritative — see
M1 §6/§17), and a fresh MaturityAssessment is computed and finalized
instead, exactly as point 8 shows is structurally permitted today.
```

This removes `draft` as a *human* review step from the MVP design.
`draft` remains only as the necessary multi-INSERT transactional
intermediate — not a state a consultant is expected to inspect and
approve before a separate "finalize" click, unless the product wants to
introduce that as a genuinely new, deliberate workflow (a real product
decision, not something the current schema/tests already establish —
flagged in §10).

## 3. Recommended lifecycle

(Restated compactly; full reasoning in §1.)

**One finalized Assessment → one atomic compute-then-finalize action.**
No standing human-reviewed draft state in the MVP. No delete-and-retry —
retry means computing a brand-new `MaturityAssessment`, leaving any
earlier flawed attempt as a harmless, permanently unfinalized orphan.
`computeAndFinalizeMaturityAssessment` (a single domain function
performing the whole sequence in one DB transaction) replaces M1 §21's
three-function split (`computeMaturityAssessment` /
`finalizeMaturityAssessment` / `discardDraftMaturityAssessment`) — see
§9 for the exact corrected blueprint.

## 4. Finding — unanswered controls

**Excluding an unanswered eligible control from the denominator, silently
and by default, is the current design's real defect, and the review
brief's concern is justified by repository evidence, not merely
plausible.** The repository already has an authoritative, pre-existing
definition of the relevant states (R-54) that M1's proposed formula did
not fully honor. The correct answer is **Option 3 in the brief's list
("incomplete / not calculable"), applied per domain, not Option 1
(exclude silently)** — with the exact mechanics in §7.

Before the scenario analysis, the three concepts the brief asks not to
conflate, made precise from the schema (none of this is new — restated
from existing tables/decisions):

- **Applicability decision** — `AssessmentControl.applicability_decision`
  (D3): `undecided | applicable | not_applicable`. Answers "is this
  Control in scope for this Engagement at all?" Set once, at Assessment
  creation, snapshotted from the locked `EngagementScope` (or defaulted
  to `undecided` if none existed) — never changes afterward
  (`assessment-controls.ts`, D3).
- **Assessment response status** — whether an `AssessmentResponse` row
  exists at all for a given `AssessmentControl`. "Not yet assessed" is
  the *absence* of a row (DECISIONS.md R-54), not a value. This is the
  concept the brief calls "unanswered."
- **Assessment rating** — `AssessmentResponse.effectiveness_rating`, one
  of `not_assessed | not_applicable | not_implemented |
  partially_implemented | implemented`
  (`db/schema/enums.ts:174-179`). Only meaningful when a response row
  exists. Per R-54, an explicit `not_assessed` row is a "deliberate,
  auditable variant" of the *same* "not yet assessed" bucket as no row
  at all — not a different bucket, and not a numeric score.
- **Maturity score** — the downstream, computed 1-5 integer
  (`maturity_scores.score`), derived *only* from ratings that fall in
  the "assessed" bucket (`not_implemented | partially_implemented |
  implemented`) via the pinned `MaturityScoringMethodology.definition.
  rating_scores` map (DECISIONS.md R-79). Never itself a proxy for
  "how much of the assessment got answered."

## 5. Evidence from repository

- **R-54** (`DECISIONS.md:1285-1307`) is the authoritative, pre-existing
  completeness model this review must not contradict: four buckets —
  *included* (an `AssessmentControl` row exists), *not yet assessed* (no
  matching response, or an explicit `not_assessed` response — same
  bucket), *assessed* (rating in the three real values), *marked N/A*
  (rating `not_applicable`). Its own rationale explicitly warns against
  "a simplistic percentage that calls N/A compliant" — the same
  integrity concern this review raises about unanswered controls
  silently vanishing.
- **`listAssessmentsForEngagement`** (`lib/domain/assessments.ts:415-460`)
  already computes and surfaces `progress: {completed, total}` —
  `completed = COUNT(DISTINCT assessment_responses.id)`, i.e. "a response
  row exists at all" — confirming completeness is already a first-class,
  product-visible reporting concept in this codebase (PRODUCT_UX_
  BLUEPRINT.md §7, quoted in that same function's docstring), not
  something this review would be inventing.
- **`finalizeAssessment`** (`lib/domain/assessments.ts:355-390`) has **no
  completeness check at all** — an Assessment can be finalized with any
  number of its `AssessmentControl` rows still unanswered. This is
  confirmed by absence: no query against `assessment_responses`, no
  guard, anywhere in the function or its migration triggers. **This
  makes "an Assessment finalizes with unanswered eligible controls" a
  real, reachable state**, not a hypothetical edge case — directly
  supporting the brief's concern that a maturity formula must not let
  this state produce a flattering, silently-partial score.
- **`MaturityScoringMethodology.definition.rating_scores`** example
  (`db/schema/maturity-scoring-methodologies.ts:44`) maps only
  `implemented/partially_implemented/not_implemented/not_applicable` —
  it does not define a numeric value for `not_assessed`. There is no
  authorized number to assign an unanswered control even if the design
  wanted to "count it as zero" — inventing one would mean fabricating a
  score value the pinned methodology never defined, which M1's own
  "free of AI/subjective scoring... do not invent" constraint already
  forbids.
- Neither PRODUCT_SPEC.md nor PRODUCT_UX_BLUEPRINT.md nor DATA_MODEL.md
  nor ARCHITECTURE.md contains the words "unanswered," "incomplete," or
  "completeness" in a Maturity context (verified by direct search) — the
  exact mathematical treatment of unanswered controls in the Maturity
  formula is a genuinely open decision, not a silently-overwritten
  existing one. R-54 constrains it (states must not be conflated); it
  does not itself resolve it for Maturity specifically.

## 6. Scenario analysis A–H

"Eligible" = `applicability_decision != 'not_applicable'` (i.e.
`applicable` or `undecided`, per D3 semantics — D3 never treats
`undecided` as excluded). "Scored" = eligible AND has a response row
with rating in `{not_implemented, partially_implemented, implemented}`.

| # | Setup | Denominator (eligible) | Numerator (scored, in the mean) | Can a score be calculated? | What it would mean |
|---|---|---|---|---|---|
| A | 20 applicable, all rated | 20 | 20 | Yes, cleanly | A complete, fully-supported domain score. |
| B | 20 applicable, 15 rated, 5 unanswered | 20 eligible, but **5 have no rating** | 15 | **Not cleanly — see §7.** Computing over 15/20 and calling it "the domain score" silently overstates completeness; the brief's exact gaming concern. | Under the recommended rule (§7): refuse, or compute *and* prominently label as partial (85% covered) — never a bare, unqualified score. |
| C | 20 applicable, 0 rated | 20 | 0 | No | Nothing scored at all → refuse (same as M1 §15 edge case #3, unchanged). |
| D | 15 applicable + 5 not_applicable, all 15 rated | 15 (the 5 N/A are excluded from the denominator entirely, not just unscored) | 15 | Yes, cleanly | A complete score over the genuinely in-scope subset — N/A controls correctly never enter either side of the fraction (R-54: N/A is not "compliant," and here it is not "incomplete" either — it is out of scope). |
| E | 15 applicable + 5 N/A, 10 rated + 5 unanswered | 15 | 10 | **Not cleanly — same as B.** | Partial: 10/15 of the *eligible* set answered; the 5 N/A never counted against completeness. |
| F | `undecided` control, no rating | Eligible (D3: `undecided` is never excluded) | Not scored (no response row) | Contributes to the "unanswered" count, same as any other unrated eligible control | This is the ordinary, expected shape for any Assessment created before a Scope was ever locked — not a special case, but it does still count toward incompleteness if a rating is genuinely missing. |
| G | `undecided` control, has a rating | Eligible | Scored | Yes, contributes normally | Applicability being undecided does not block scoring — D3 already established this (M1 §5); a real answer is a real answer regardless of the Scope decision's own status. |
| H | `not_applicable` control, has a rating | **Not in the denominator at all** | **Not in the numerator** | The rating is ignored for maturity purposes | The applicability decision wins over the presence of a rating — an assessor may record a rating out of habit or before N/A was decided, but D3's applicability decision is definitive for scope; scoring an explicitly-excluded control would silently reintroduce out-of-scope content into the score, exactly what D3 was built to prevent (M1 §5, D3's own "membership never filtered, but applicability gates the calculation" principle). |

## 7. Recommended denominator/numerator semantics

**Unanswered eligible controls must never be silently excluded and
folded into a denominator that looks complete. They must make the
affected domain's completeness explicit, and by default block that
domain's score from being computed until it is complete — with an
explicit, deliberate override path for a genuinely partial computation,
never an implicit one.**

Reasoning, directly against the brief's four options:

1. *Exclude entirely* — **rejected.** This is what M1's original formula
   did (`eligible_controls = ... AND response.rating IS NOT NULL`,
   silently), and it is exactly the gaming vector the brief names: an
   organisation (or a consultant under schedule pressure) improves its
   score by simply not answering the hard controls, since only the
   answered ones are averaged.
2. *Count as zero* — **rejected.** Would fabricate a numeric value the
   pinned methodology's own `rating_scores` map does not define for
   `not_assessed` (§5), and would conflate "no decision was made" with
   "the worst possible decision was made" — precisely the distinction
   R-54 already goes out of its way to keep separate for
   `AssessmentResponse` itself. Silently defaulting to the worst score
   is not more honest than silently excluding; it is a different
   fabrication.
3. **"Incomplete / not calculable" — recommended, per domain.** A
   domain's `MaturityScore` requires every one of its eligible
   (`applicable` + `undecided`) mapped controls to have a real rating in
   `{not_implemented, partially_implemented, implemented}`. If even one
   is missing, that specific domain is not computed (no `MaturityScore`
   row for it, same "no row, never a fabricated number" posture M1 §15
   already established for the all-unanswered case — this generalizes
   it to the *partial*-unanswered case, which M1 had missed).
4. *Some other handling* — the one refinement worth adding on top of
   (3), not a fourth alternative to it: a `--allow-partial` computation
   mode for a domain that is missing a *small, explicitly acknowledged*
   number of responses, which computes the mean over only the answered
   eligible controls but **must** record, on the `MaturityScore` row's
   traceability data, exactly how many eligible controls were excluded
   for lack of an answer and their ids — never a bare, unqualified
   number. Whether MVP offers this override at all, or requires 100%
   response completeness before any domain can be scored, is the one
   remaining product call — flagged as Open Decision #1 in §10, not
   silently decided here, because there is a real, currently-unresolved
   tension between "operationally useful for an in-progress engagement"
   and "never inflates a score by omission."

Either way, the **default**, unqualified compute path must refuse a
domain (and therefore the overall score, which cannot honestly average
over an incomplete domain either) rather than silently narrow its own
denominator.

## 8. Exact revised formula

```
for each MaturityDomain D mapped to this methodology:
  mapped_controls = AssessmentControls in this Assessment
      where control_id in MaturityDomainControlMapping(D)

  eligible_controls = [ c in mapped_controls
                         where c.applicability_decision != 'not_applicable' ]
      // 'applicable' and 'undecided' are both eligible (D3: undecided
      // never excludes). 'not_applicable' controls are removed from the
      // denominator entirely — scenario D/H.

  if eligible_controls is empty:
      skip domain (no MaturityScore row)          // unchanged from M1 §15 #4

  scored_controls = [ c in eligible_controls
                       where exists AssessmentResponse for c
                         and response.effectiveness_rating in
                             ('not_implemented','partially_implemented','implemented') ]

  unanswered_controls = eligible_controls - scored_controls
      // "unanswered" = no response row, OR a response row with rating
      // 'not_assessed' (R-54: same bucket) — scenario B/E/F.

  if scored_controls is empty:
      skip domain (no MaturityScore row)          // unchanged from M1 §15 #3

  if unanswered_controls is not empty:
      // Recommended default: refuse this domain entirely — completeness
      // is a per-domain precondition for a defensible score, not merely
      // a caveat attached after the fact.
      //   -> no MaturityScore row for D; surfaced to the caller as
      //      "incomplete: N of M eligible controls unanswered", so the
      //      compute action can report it, never silently drop it.
      // If Open Decision #1 (§10) resolves in favour of an explicit
      // partial-compute override:
      //   -> compute over scored_controls only, AND persist
      //      unanswered_controls' ids/count on the MaturityScore row's
      //      traceability data so the gap is part of the permanent
      //      historical record, never invisible.
      handle per the resolved product decision — do not silently proceed
      as if unanswered_controls were empty.

  else:
      control_scores = [ rating_scores[c.response.effectiveness_rating]
                          for c in scored_controls ]
      domain_score = round_half_up( mean(control_scores) )
      write MaturityScore(domain=D, score=domain_score, ...)

overall_score = round_half_up(
  sum( domain_score[D] * MaturityDomainWeight[D] for D in SCORED domains only )
  / sum( MaturityDomainWeight[D] for D in SCORED domains only )
)
  // A domain skipped for incompleteness or emptiness is excluded from
  // the overall the same way an all-unanswered domain already was in M1
  // §19 — this is not a new rule, only a wider set of domains it now
  // correctly covers.
write MaturityScore(domain=null, score=overall_score, ...)
```

This is a strict narrowing of M1 §19's formula (the eligibility/
exclusion logic for `not_applicable` and empty-domain handling is
unchanged); the only substantive change is that `unanswered_controls`
is now computed and checked explicitly, rather than the earlier
`AND response.rating IS NOT NULL` filter silently doing the same
narrowing with no visibility or gate.

## 9. Impact on the M1 recommendation

Two corrections to `M1_MATURITY_DESIGN.md`, both narrowing what was
proposed there — nothing in M1's Executive Summary, control-scoring
table (§4), scope semantics (§5), weighting (§10), scale (§11), or
alternatives (§20) is affected:

1. **§19/§8 formula** — superseded by §8 above: unanswered eligible
   controls are no longer silently excluded from the denominator; a
   domain with any unanswered eligible control is refused by default
   (or, if Open Decision #1 resolves otherwise, computed with the gap
   explicitly recorded) instead of quietly averaging over whichever
   controls happened to be answered.

2. **§21 Implementation Blueprint, REQUIRED FOR MVP list** —
   `discardDraftMaturityAssessment` is **withdrawn**; it described a
   capability ("delete a draft, correct it, recompute in place") the
   current schema and grants do not support (§1 point 7). The corrected
   REQUIRED FOR MVP domain function set is:
   - `computeAndFinalizeMaturityAssessment(assessmentId)` — single
     transaction: compute every eligible domain (applying §8's
     completeness gate), insert the `MaturityAssessment` header
     (`draft`), insert its `MaturityScore` rows, then finalize — no
     separate "review as draft, finalize later" application step for
     MVP (see Open Decision #2, §10, for whether a later milestone
     should add one).
   - Read functions (list/detail) — unchanged from M1 §21.
   - No `discardDraftMaturityAssessment` and no `finalizeMaturity
     Assessment` as a *separate*, independently-invokable action for
     MVP — folded into the one atomic function above, consistent with
     §1's finding that no real workflow exists between "compute" and
     "finalize" today.
   - The narrow migration M1 §21 already flagged as needed (RLS/
     permission policies tied to a new `maturity.compute`/
     `maturity.finalize`-shaped permission) is unaffected by this
     review and remains necessary.

Nothing else in M1's recommended methodology, data model impact
assessment (§18 — "zero schema changes required" **still holds** for
the MVP calculation engine itself; a schema change would only be needed
if Open Decision #3 below is resolved in favour of a supersession
column), or alternatives analysis needs to change.

## 10. Any remaining open decision

1. **Refuse-if-incomplete vs. explicit partial-compute override (§7).**
   Does MVP require 100% response completeness per domain before any
   score is computed at all (simplest, strictly gameproof, but may be
   operationally frustrating for a large in-progress engagement where a
   handful of controls are still pending), or does it offer a
   deliberate, explicitly-logged partial-compute path? This is a
   product/methodology call, not an engineering one — this review
   recommends refuse-by-default as the MVP starting position (it is the
   simpler rule to implement and explain to a client, and strictly
   satisfies the brief's anti-gaming requirement) with the override as
   an explicit, clearly labeled future enhancement rather than an MVP
   requirement.

2. **Should a human review step exist between "computed" and
   "finalized"?** §1's recommended lifecycle collapses these into one
   atomic action because nothing in the current schema, tests, or
   documentation shows a review step was ever intended (draft's only
   proven purpose is the multi-INSERT transaction window). If the
   product wants a genuine "compute now, a consultant reviews and
   approves before it becomes historical" workflow, that is a new
   product decision requiring a new mechanism (e.g., an explicit
   approval action, mirroring D3's `scope.lock` or Assessment's own
   `finalize`) — not something to infer from the existing immutability
   grants, which currently argue *against* an editable review window
   existing at all (§1 point 5).

3. **Same-Assessment recomputation (§1 point 8).** Should the
   application block creating a second `MaturityAssessment` for an
   `assessment_id` that already has a finalized one, to avoid ambiguity
   about which is authoritative for reporting? Or is multiplicity
   intentional (e.g., re-running under a corrected methodology)? If the
   product wants an explicit, auditable correction/supersession
   relationship, the precedent already exists elsewhere in this
   codebase — `Risk.previous_risk_id` and D3's own
   `EngagementScope.previous_scope_version_id` — and a
   `previous_maturity_assessment_id` self-reference would be the
   natural analogue. This is a schema change and is explicitly NOT
   proposed for implementation here; it is named only as the shape a
   future decision would likely take if the product decides
   multiplicity needs to be made explicit rather than left as an
   unconstrained possibility.

4. **Where does "N of M controls unanswered" get surfaced to a human?**
   §7/§8 require the gap to be visible, not silently dropped, but this
   review does not specify UI/reporting placement — that belongs with
   M1 §16's reporting-integration design (governance-signals list),
   unaffected in shape by this review, just fed a genuinely new signal
   (per-domain completeness) it did not previously carry.
